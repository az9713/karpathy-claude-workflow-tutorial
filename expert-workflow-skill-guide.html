02 / The actual job

This skill builds other skills.

build-expert-workflow is a builder. You provide an expert, a specific capability, source access, and success criteria. It produces a reusable task skill grounded in observable methods. It does not begin with a finished expert agent, train new model weights, or reconstruct a person’s mind.

01

Scope

Name the expert and one task. Define who will use the result and what success means.

02

Audit

Inventory accessible sources, authorship, dates, permission, and missing material.

03

Derive

Extract procedures, cues, exceptions, and revision conditions with source locators.

04

Package

Write a task SKILL.md, evidence reference, and evaluation cases.

05

Evaluate

Check grounding and task quality on fresh cases; measure fidelity only when possible.

06

Update

Ingest new evidence, revise affected methods, preserve history, and retest.

A useful rule is conditional: “When X appears, inspect Y, compare A and B, and revise if Z.” A slogan such as “think deeply” does not specify observable behavior. The builder does not force seven rules or transfer Karpathy’s rules to every field.

Expect a portable folder with SKILL.md, references/evidence.md, and evaluations.md. A compact hot page is optional when the evidence becomes large. If the sources cannot support the requested reconstruction, expect a gap report instead.

03 / Selection, not magic words

What are the trigger phrases?

The skill’s name is build-expert-workflow. Its description supplies the selection cues. There is no separate hard-coded trigger-word list. The following phrases express the intended scope; they are suggested wording, not measured activation guarantees.

Useful wording and the intent it communicates
PhraseIntent
“Build an expert workflow”Create a reusable method from a named expert’s evidence.
“Turn this expert’s publications into a skill”Convert sources into operational instructions.
“Create a source-grounded teaching skill”Build a bounded teaching capability with citations.
“Extract documented methods from these worked cases”Identify observable procedures rather than imitate writing style.
“Build a provisional skill from sparse sources”Adapt scope and claims to incomplete evidence.
“Update this expert-method skill with new evidence”Revise an existing package and recheck affected cases.

Weak cues: “Explain physics,” “summarize this paper,” or “think like Feynman” do not clearly request skill construction. A source-summary or teaching skill may be a better match. Add the named expert, concrete capability, and request to create or update a reusable skill.

The installed description

Build or update a reusable, evidence-grounded skill for applying a named expert's methods to a specific task without arranging interviews. Use when adapting publications, worked cases, existing recorded interviews, or authorized materials into a teaching, review, research, or decision workflow, including sparse or restricted source collections.

This text comes from the installed SKILL.md. The examples clarify its scope; they do not change the skill’s routing configuration.

04 / Copy and adapt

Natural-language requests for different situations.

Each request supplies a task and constraints. Replace bracketed fields and example folders. These are request templates; no named-expert skill or case result below has been generated.

Rich corpus · documented teaching methods
Build an expert workflow based on Andrej Karpathy's documented teaching methods for explaining a tiny neural network. Use the authorized sources in ./sources/karpathy and accessible primary material. Create a reusable teaching skill for a technically experienced learner. Separate direct statements from inferred methods, cite source locators, and include a fresh task that tests application rather than reciting the rules.
Sparse corpus · narrow provisional skill
Use the build-expert-workflow skill for [expert name], focusing on reviewing [specific kind of research proposal]. I only have two articles and one recorded talk in ./sources. Build the narrowest provisional skill those materials support. Count shared-origin material once, identify missing evidence, and do not invent recurring rules or arrange interviews.
Worked cases · reconstruct decisions
Turn [expert name]'s annotated worked cases in ./cases into a reusable review skill. Focus on which cues distinguish accepted and rejected designs, which alternatives were considered, and what evidence changed a decision. Preserve exceptions. Leave absent explanations unknown. Reserve one case for evaluation before extracting methods.
Restricted sources · access audit first
Use build-expert-workflow to plan a skill for [expert name] reviewing [task]. Some sources have processing restrictions. Inventory their permissions and metadata first; do not open restricted content or upload it until the intended processing environment is authorized. Use permitted public sources meanwhile. Carry applicable restrictions into derived notes and the resulting skill.

Local storage alone does not establish permission for model processing. If a source is local-processing-only, the workflow needs an approved processing environment before ingestion.

Almost no evidence · honest feasibility check
Assess whether a source-grounded workflow can be built for [expert name] performing [task]. I cannot interview or contact anyone. Search accessible sources and audit what they actually establish. If the evidence is insufficient, produce a gap report and suggest a clearly labeled generic domain workflow as an alternative. Do not fabricate a named-expert skill.
A useful prompt includes four things.

Expert + bounded task + permitted sources + observable success criterion. “Build another [expert]” alone leaves all four underspecified.

05 / After the first build

Update the package, evaluate it, then invoke the result.

Update an existing expert skill
Use build-expert-workflow to update the expert-method skill at ./expert-skills/[folder] using the new authorized sources in ./new-sources. Record provenance, identify methods affected by the new evidence, preserve contradictions and prior versions, and rerun affected evaluation cases. Keep outputs local.
Evaluate without access to the expert
Use build-expert-workflow to evaluate the skill at ./expert-skills/[folder]. Compare the same model and tools on fresh tasks with and without the skill. Check source attribution, task outcomes, exceptions, and appropriate abstention. We have no expert reference answers, so report fidelity as unmeasured. Agree on a bounded test budget before any additional paid runs.

Building and using are different requests. Once a resulting task skill is installed and discoverable, invoke its own name to perform the task. The builder is appropriate for construction, evidence updates, or evaluating the package.

Use the generated skill · natural language
Use the [generated skill's actual name] skill to review the worked solution in ./drafts/solution.md. Apply only methods supported by its evidence reference, cite the relevant source locators, and identify assumptions, exceptions, and unsupported judgments.

Take the generated name from its SKILL.md. That skill does not exist merely because this guide shows a template. In Claude Code use its /actual-name; in Codex mention $actual-name.

06 / What the corpus permits

Sparse evidence changes the claim.

The workflow needs no new interviews. It can use existing public recordings, papers, books or excerpts you may process, code, annotations, correspondence you are authorized to use, and documented decisions. It cannot infer hidden methods from fame or from the model’s recollection.

The supported result depends on evidence quality and relevance
Evidence routeSupportable result
Relevant primary materialDocumented methods within the observed task and context.
A few primary itemsNarrow, provisional methods; single-source support remains visible.
Existing case accountsObserved decision procedures, with self-report and inference distinguished.
Mostly secondary materialA labeled proxy reconstruction; commentary is not direct expert testimony.
No usable evidenceA gap report. A generic alternative needs its own honest label.

Every method carries a trigger, procedure, supporting source and locator, attribution status, exceptions, and validation status. “Two sources” does not mean independent support if both repeat one original talk. Even independent repetition does not prove a method is correct.

Verification follows the field: runnable tests for code, derivations and counterexamples for mathematics, observations and controls for empirical science, and appropriate review for judgment-heavy tasks. The skill’s instructions are a verification policy; they are not an installed enforcement hook.

08 / Validation boundary

Know which claim was checked.

The skill’s structure and reference links have been checked, and installed copies match the source. The invocation syntax is documented by the platform providers. These checks do not establish activation rates or expertise fidelity.

The Feynman oscillator skill has now been created, with a worked lesson and passing mathematical fixtures. The other named-expert requests remain templates. Controlled model comparisons, learner benefit and expert fidelity remain unmeasured; a syntax validator cannot establish that an assistant reasons like an expert. Read the Feynman evidence and evaluation report for the actual status.

Three separate questions for a real pilot
QuestionEvidence needed
Is it grounded?Check methods and attributed claims against the sources and locators.
Does it help?Compare observable task quality with a baseline on fresh cases.
Is it faithful?Compare with expert reference decisions where available; otherwise leave fidelity unmeasured.

Start with a capability you can check.
A narrowly scoped skill that improves a review or explanation is easier to assess than a broad claim to have “built another expert.”

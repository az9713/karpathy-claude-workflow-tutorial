How a general expert-workflow builder became a Feynman oscillator skill.

build-expert-workflow supplied a method for investigating and packaging expertise. The assistant applied it to one expert, one teaching task, a bounded collection of sources, and physics-specific checks. The result was a new set of instructions another agent can read and use.

The central operation: identify something observable in a source, decide when it is useful, turn it into an instruction, retain its attribution and limits, and define a check that could expose failure.

This page explains the recorded build and the files it produced. The worked transformations below clarify the reasoning; they are not claims that an automated compiler or an undocumented intermediate tool ran.

1. What actually happened when the builder was invoked?

The original request supplied the target and constraints:

$build-expert-workflow
Create a reusable skill from Richard Feynman's documented methods
for explaining a harmonic oscillator. Use ./sources and accessible
public material. Do not arrange interviews. Record source support,
coverage gaps, and evaluation tasks.

The assistant read the builder's SKILL.md, along with its source-access and evaluation references. Those Markdown files describe decisions to make and records to keep. The assistant then used ordinary tools to inspect files, retrieve public pages, write the new files, execute checks, and inspect an HTML report.

There was no separate software function that automatically converted “Feynman” into a finished skill. The model interpreted the builder's instructions and made task-specific research and synthesis decisions. The durable output is readable text plus a small check script. No model weights were trained or changed.

  1. General recipeThe builder defines the evidence and packaging discipline.
  2. Specific evidenceThe request and sources constrain what can be attributed.
  3. Derived proceduresThe assistant writes conditional methods and domain checks.
  4. Reusable bundleA future agent loads the new skill to perform the teaching task.

Creation time and use time are different. At creation time, the builder guides the assistant in constructing the package. At use time, an agent reads feynman-harmonic-oscillator/SKILL.md and its relevant references. The builder does not need to run again for every oscillator explanation.

Construction instructions: builder entrypoint, source-access guidance, evaluation guidance. The installed and project copies of the builder entrypoint were verified to have matching SHA-256 hashes when preparing this walkthrough.

4. Trace one source passage into an operating instruction

M2 is a useful example because its instructional value comes from an observable sequence of operations.

A · Observation

What the lecture does

In section 21-2, the exposition tries amplitude scaling, finds that it preserves the normalized equation, and changes the time scale instead. It verifies the candidate by differentiating. S21, Eqs. 21.2–21.4.

B · Interpretation

What can be reused

A teaching procedure can distinguish the effect of two transformations, test which equation each satisfies, and connect the successful transformation to physical parameters. Calling that a reusable method is the builder's inference.

C · Conditional instruction

When it should apply

For a free linear spring oscillator, distinguish amplitude scaling from time scaling and substitute the proposed solution. Use the starting data and energy as checks. The condition matters: nonlinear forces can invalidate the amplitude-independent period.

D · Evaluation

How failure could be exposed

Give the agent changed mass, stiffness and starting data. Require the correct frequency, both starting values, energy, and the consequences of doubling both initial values. A wrong frequency or energy relation should fail the grader.

The translation in compact form 
Evidence locator:
  S21, section 21-2, Eqs. 21.2–21.4

Observed contrast:
  A*cos(t) still satisfies x'' = -x.
  cos(omega0*t) satisfies x'' = -omega0^2*x.

Derived instruction:
  When explaining free linear motion, distinguish amplitude from
  time scaling and verify the proposed solution by substitution.

Attribution:
  Inferred procedure from edited exposition.
  No claim that Feynman stated this as a universal personal rule.

Application check:
  T2: m=2, k=18, x0=0.3, v0=-0.6.
  omega0=3; x(t)=0.3*cos(3t)-0.2*sin(3t).

The first expressions use the lecture's normalized setting. T2 is a newly authored application with physical units in the evaluation file. Passing its arithmetic does not establish that a model will follow the teaching method.

The actual skill entrypoint condenses this into M2. The longer ledger entry preserves support, scope and stopping conditions. This separation keeps the operational instruction readable while making its origin inspectable.

A second transformation: approximation into an explicit boundary

In chapter 24, an approximate weak-loss prediction is followed by an exact solution whose oscillation frequency differs from the initial guess. The construction turns that contrast into M4: identify the regime, compare the approximation with exact roots, and stop using a damped-cosine form when the roots are no longer oscillatory. S24, section 24-2, Eqs. 24.10–24.17; section 24-3.

T5 then asks for classification at omega0=3 and gamma=1, 6, 8. Those values test whether an explanation respects underdamped, critical and overdamped regimes. They were authored by the builder; they are not undisclosed Feynman reference answers.

5. Three kinds of content entered the new skill

This distinction is the main defense against attaching a famous name to generic model output.

Content typeExample in this packageWhat attribution is justified?
Observed source behaviorM1–M5 generalize worked exposition.Documented examples support a bounded procedural inference. Exact sentence authorship and an invariant personal rule are not established.
Explicit teaching self-reportM6 uses the preface's distinction between a core and extensions, and deductions and newly introduced ideas.A stated teaching preference; its effectiveness still needs testing. SP, paragraphs beginning “For this reason” and “At the same time.”
Builder-supplied scaffolding and physicsThe operating loop, learner transfer question, evaluation protocol, parameter fixtures, units checks and corrective derivations.Generic task design or physics reasoning by the builder. These additions are not new historical evidence about Feynman.

The preface explicitly describes the lectures as edited. That limits claims about original wording and delivery. The skill accordingly treats its method names as labels created for this package. Feynman's Preface, opening paragraph.

A source can be authentic and still need qualification. The ledger preserves the passage about transients dying away beside an undamped equation. The skill supplies the damping condition rather than repeating it unqualified. Mathematical correctness and faithful attribution are separate checks.

The six methods were chosen for available support. The builder did not prescribe six, seven, or any other fixed count. Karpathy's seven rules from the earlier demonstration were not imported into this physics skill.

6. How the decisions became files

skills/feynman-harmonic-oscillator/
├── SKILL.md                 Discovery, scope and operating instructions
├── references/evidence.md   Sources, attribution, contradictions and gaps
├── evaluations.md           Prompts, graders, baselines and actual status
├── scripts/check.py         Runnable mathematical and reference checks
└── overview.html            Human-readable handoff

The builder required the first three files. The script was added because the task had mathematical claims that could be checked cheaply and repeatably. The HTML provided the human-facing delivery. No retrieval database, wiki, agents, hooks or enforcement service was needed for this small corpus.

The entrypoint's YAML name and description tell a skill-aware host what the capability is and when it applies. The body directs the agent to the methods and references. This build created a portable local folder; it did not install the skill globally or prove automatic discovery in a host.

A useful way to inspect the package is to start at a method in SKILL.md, follow its source ID into the ledger, inspect the original passage, then examine a task that could reveal misuse. That chain is the main reusable asset.

Eleven tasks were specified. T7–T10 address conflicting evidence, unsupported attribution, fitting versus validation, and malicious instructions inside a purported source. They exist as prompts and graders; their existence is not a passing result.

T1 repeats an extraction example. The other values and adversarial cases were designed after extraction. They are fresh applications but not a preregistered, independently held-out evaluation corpus. That is a real limitation of this first build.

The comparison that would demystify added value further

B0 · Base model

Same model and tools, without the skill or source retrieval. This provides an ordinary-answer baseline.

B1 · Retrieval only

Same model and tools, with the audited passages but without the derived procedures.

B2 · Retrieval plus skill

Same source access as B1, plus the new skill instructions.

Compare B1 with B2

Hold source access constant to test whether procedural guidance helps. B0 versus B2 mixes knowledge access with method gains.

Use fresh contexts and keep model version, settings, prompts, tools and budgets fixed. Keep the grader's answer key out of the model context. An instructor or learner should assess whether an explanation transfers to a changed case; model self-scores alone are insufficient. This design is recorded in evaluations.md and remains a planned experiment.

8. How to specialize the same builder for another topic

The general process is reusable; the evidence and tests must change.

  1. Specify one capability. Name the expert, the task, the audience and a concrete success criterion. “Explain this oscillator” has a usable boundary; “become Feynman” does not.
  2. Find observed procedures. Prefer worked cases containing a choice, a rejected alternative, a check or a correction. A biography or a reputation is weak support for an operating method.
  3. Write conditional instructions. Preserve when each method applies and where it stops. Retain locators and distinguish direct statements from your inferences.
  4. Choose the domain's checks. For physics use derivations and relevant observations; for code use tests; for other fields choose outcome measures or qualified review appropriate to the task.
  5. Design transfer and failure cases. Include a routine task, unfamiliar application, exception and beyond-evidence request. Plan evaluation cases before extraction where feasible to improve separation.
  6. Package and report honestly. Keep the skill, evidence and evaluation records together. State what ran and what is unknown. Expand scope only when new evidence and evaluation justify it.
$build-expert-workflow
Create a reusable skill for [expert]'s documented methods for [bounded task].
Audience: [learner or operator].
Success: [observable output or outcome].
Use [authorized local sources] and accessible public primary material.
Do not arrange interviews.
Record source locators, attribution, coverage gaps and conflicting evidence.
Separate expert-supported methods from generic domain checks.
Design transfer, exception and insufficient-evidence evaluations.
Report actual test results and leave unmeasured claims explicit.

This is a reusable prompt template derived for this walkthrough, not an additional command executed during the Feynman build.

THE MOTIVE00:38 01:12

Build an explanation you can reason with

The video's motivating problem is familiar to anyone building with an AI coding assistant: an answer can be fluent, the code can be plausible, and the user can still lack a working explanation of what happened. Herk frames that gap as a practical liability. If you cannot explain the mechanism, you are poorly equipped to diagnose the code when it breaks or to decide whether it is ready for a client.

His opening illustration asks an assistant to explain the difference between an API and MCP. The screen then shows a restaurant analogy and a dissatisfied follow-up. The example establishes the learning problem; the analogy itself is not a technical definition.

Opening illustration: ask for an explanation
01:15
Can you explain what the difference between API and MCP is?
Opening illustration: the learner is still confused
01:20
That doesn't make sense at all

Herk's proposed response is to put a teacher's public methods into the assistant's working environment. At 00:46, he describes an agent that follows rules distilled from Karpathy's writing and lectures. The “brain” language is a metaphor: the demonstrated mechanism is a collection of sources, a derived wiki, and instructions controlling how a model approaches a task. The transcript does not describe training new model weights or transferring a person's mind.

By 01:50, the argument broadens. You do not need to be an expert in every subject to assemble an environment informed by expert work. The aim is to use that environment to understand a problem, then reuse the accumulated knowledge in your own skills, agents, and workflows. Herk presents the pattern as transferable to other teachers, authors, and coaches.

01 / EVIDENCE02:48

Gather the sources before interpreting them

The first build step collects Karpathy's public blogs, repositories, lecture captions, and X posts. Herk names youtube-transcript-api and yt-dlp for YouTube captions, and TwitterAPI.io for X. He reports a crawl taking roughly 45 minutes to an hour and producing more than 700,000 words. He also reports spending about one dollar on the X retrieval. Those are figures from his demonstration, rather than a current price quote or a measurement reproduced here. 03:11 03:32

The important design choice is preservation. Each source family gets its own raw subfolder and a manifest listing files, word counts, and failures. The instruction to postpone summarization keeps the original evidence available for later checking. It also makes missing retrievals visible instead of allowing a polished synthesis to conceal them.

Prompt 01 / The crawl
03:35
Go get everything Andrej Karpathy has put out publicly. His blog and his repos straight from GitHub. The caption transcripts of his YouTube lectures with youtube-transcript-api and yt-dlp. His X posts with the TwitterAPI.io key in my .env file. Run one agent per source so they work in parallel. Save all of it raw into a folder called karpathy-brain/raw, one subfolder per source, and write a manifest in each one listing every file with its word count and anything that failed. Don't summarize anything yet.

The request to run one agent per source is a way of parallelizing acquisition. It is separate from the intellectual task of deciding which statements deserve to become rules. A large corpus supplies material for that task, but word count alone does not establish teaching quality.

02 / ORGANIZATION03:56 04:43

Compile a navigable wiki from the raw corpus

A folder containing hundreds of thousands of words is cumbersome to query. The second prompt asks the model to compile it using the LLM-wiki framework referenced in Karpathy's gist. The raw layer stays untouched, while a separate layer contains an index, an activity log, pages for individual sources, and pages for principles and methods. A compact “hot page,” limited to fewer than 500 words, provides an initial orientation.

The video shows this material in Obsidian and explicitly says Obsidian is optional: it serves as the visual interface for the wiki. The underlying value lies in the relationships. A rule links back to the sources supporting it, and a source links to the rules it supports. New evidence can be incorporated into that network rather than appended as an isolated note. 04:50 05:15

Prompt 02 / The wiki
04:45
Here's Karpathy's LLM wiki gist.
gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
Use it as the framework and compile everything in karpathy-brain/raw into a wiki of his brain. I want an index, a log, one page per source, pages for his principles and his methods, and a hot page under 500 words that answers most questions about how he thinks. Every claim about him needs a quote from the raw files. Never edit anything in raw.

Two constraints carry much of the design. Claims about Karpathy must be tied to quotations in the raw files, and the raw files must never be edited. In this workflow, the wiki is an interpretation that can be revised; the original corpus is the record against which revisions can be checked. The hot page and later five-page reading limit also create a deliberate budget for what the agent reads on an ordinary task.

03 / TEACHING BEHAVIOR05:37

Turn recurring methods into explicit rules

The next step moves from knowing what a teacher has said to specifying how the assistant should act. Herk asks for the seven strongest rules, with each supported by an exact quotation and appearing in at least two different places. This is a recurrence threshold intended to prevent a single remark from being promoted into a general principle.

Prompt 03 / The rules
05:48
Read the wiki and write his rules for how he builds and how he teaches. Only keep a rule if it shows up in at least two different places, like his blog and a lecture. Every rule needs an exact quote from him with the source it came from. Give me the seven strongest ones.

The seven rules below are the video's synthesis of Karpathy's methods. Their original supporting quotations are not all reproduced in the supplied transcript, so this document attributes the synthesis to the demonstration rather than claiming an independent audit of every underlying source.

1Build it or you don't understand it. The learner should encounter the mechanism through a working construction. In the demonstration, that means a small implementation whose behavior can be inspected. 05:53

2First-order term first. Find the part that does the essential work, show it functioning, then introduce one additional ingredient at a time. The transcript explains this as a way of keeping the causal contribution of each addition visible. 05:58

3Predict, then run, then compare. State the expected result before execution and confront it with the observed result. A program can run while still behaving incorrectly; an explicit prediction makes that discrepancy easier to notice. 06:02

4Show the wrong version first. The video treats bugs as teaching material. A broken version, followed by diagnosis and repair, reveals why the correct version needs its particular structure. 06:11

5Prove it, don't claim it. The agent should produce execution evidence that the learner can inspect. The narration connects this rule to the problem of handing over code with an unsupported claim that it works. 06:19

6Say what you assumed. Assumptions must be exposed so the learner can check whether the agent solved the intended problem. The later ingestion example extends this into asking questions when a request provides too little information. 06:21 09:44

7Simpler wins. Complexity should earn its place. The later review demonstration applies this by removing unnecessary parts and comparing the resulting behavior with the original. 06:27

At 06:35, Herk describes a further boundary: when there is no direct source for a claim, the agent must identify it as an inference. That distinction matters because an assistant can easily make a plausible recommendation sound like something the named expert actually said.

04 / EXECUTION STRUCTURE06:43

Give the method a reusable entry point

The fourth prompt packages the rules into two components. A karpathy subagent handles the work with its own instructions and bounded reading context. A karpathy-teach skill receives the user's request, hands it to that agent, and grades the returned answer against the seven-rule checklist before presenting it. This is the division of labor described by the video; the demonstration does not establish that a model grading its own workflow is an independent verification system.

Prompt 04 / Two files
06:50
Turn these seven rules into a Claude Code subagent called karpathy. It reads the wiki's hot page first, never reads more than five wiki pages, follows the seven rules on every task, cites the wiki page for anything it says about him, and ends every answer with what it ran, what came out, and what it changed. Then make a skill called karpathy-teach that hands any task to that agent and grades the answer against the seven rules before showing it to me.

The agent reads the hot page first and no more than five wiki pages. It must cite the wiki for statements about Karpathy and finish with an account of what it ran, what came out, and what it changed. These are concrete behavioral commitments that can be inspected in an answer.

The skill's generic invocation is deliberately short. The accumulated corpus and instructions supply context that the learner would otherwise need to repeat in every request. 07:08

Reusable command template
07:16
/karpathy-teach [what to build or explain]
05 / VERIFICATION07:26 07:43

Make execution a condition of finishing

The fifth prompt adds a Stop hook, described in the transcript as a small script invoked when the agent attempts to finish. It applies specifically to turns using the Karpathy agent or teaching skill. If a code file was written or edited and nothing was run afterward, the proposed hook blocks completion and sends the task back with an instruction to run the code.

Prompt 05 / Run gate
07:45
Add a Stop hook to this project. When a turn used the karpathy agent or the karpathy-teach skill, and a code file was written or edited but nothing was run afterward, block the stop and send it back with the message: Karpathy rule, run it before you say it works. Leave every other session alone.

This is the point where a teaching rule becomes a requested runtime constraint. “Run it before you say it works” is no longer only an aspiration in the system instructions; the creator asks for an enforcement mechanism around finishing the turn.

Interpretation: a run gate checks for execution, while correctness depends on what was executed and what the result establishes. An unrelated command or an irrelevant test would be weak evidence. The prompt specifies the desired gate, but the transcript does not expose enough of its implementation to prove how precisely it detects relevant execution. The subsequent demonstrations show why predictions, meaningful inputs, and observed outputs must accompany the gate.

06 / THE LEARNING LOOP08:08

Test the teacher on a tiny tokenizer

To test the setup, Herk requests a tiny byte-pair tokenizer built from scratch. The transcript describes a tokenizer as the component that turns text into numeric input for a language model. This example gives the agent something small enough to implement and execute while explaining each step.

Test command / Build and teach a tokenizer
08:13
/karpathy-teach build me a tiny byte-pair tokenizer from scratch and teach me what it does

Extraction detail: the introduction shows a numbered “06 / The test” card at 02:52, with its body blurred. The command above was recovered from the readable demonstration at 08:13; it is not a claimed exact transcription of the blurred card.

The sequence is the important result. First the agent defines what “done” means. It builds the smallest version on a tiny input, states an expected output, executes it, and shows the actual output. It then presents a broken version, explains the failure, fixes it, and records what ran, what changed, and which teaching rules motivated those actions. 08:16 08:24 08:32

A learner can follow the causal chain from a prediction to an observation and then to a repair. Herk's claim is that this provides a better basis for understanding than receiving a finished code block alone. The footage is an example of that behavior, rather than a controlled comparison measuring learning gains across users or tasks.

APPLICATION / CODE REVIEW08:47

Ask what the implementation can actually withstand

The same teaching method is used for review. Herk shows a YouTube-comment script that had previously run successfully in the assistant's test setting. The reviewer predicts that it will fail when printing an emoji in a normal Windows console, then the demonstration reproduces that failure before the script writes its files. The successful earlier run was therefore evidence about one environment, not every environment in which the code might be used. 08:55 09:03

Review command / Would he accept it?
09:00
/karpathy-teach review projects/youtube-videos/karpathy-claude-agent/research/test-runs/plain/flag_questions.py the way Karpathy would review it. Would he accept it? What would he delete?

The reviewer also trims parts of the implementation that are not contributing to the task. According to the narration, it runs the original and the trimmed version on the same inputs and displays their outputs side by side, checking that the simplified version still catches the same questions. This gives “simpler wins” an operational meaning: preserve the relevant behavior while reducing unnecessary machinery. 09:12 09:20

The review's delegated instructions are visible earlier in the video, at 07:20. They add several useful details: restrict source reading, cite the principle behind each teaching move, compare real outputs, and finish with an explicit acceptance verdict and a justified list of deletions. In the block below, the creator's repository name and absolute machine path have been replaced with portable project placeholders.

07:20
Read _hot.md first. Five wiki pages maximum. Never read raw/.

Follow the loop in your agent file. End with the proof block.

Notes for this run: the file is in your project repository at <YOUR_PROJECT_DIRECTORY>. This is a review, so the "build" is the reviewed and trimmed version. The broader lesson is that a success claim needs conditions. Input, terminal encoding, and execution environment can change what a passing run tells you. In the video, the predicted failure is valuable both as a review finding and as an explanation the learner can inspect.

The final demonstration adds an X post using karpathy-ingest. The post concerns a long voice ramble that an LLM helps clean into clearer text. The agent checks whether the post is already in the raw corpus, writes a source page, and updates the related pages instead of requiring the user to maintain the wiki's relationships by hand. 09:35 09:40

Herk reports two effects. The rule about assumptions gains a behavior: ask a couple of questions when the user's request is thin. A candidate rule with only one supporting source gains a second source and is promoted into the accepted set. The agent then updates the index, the hot page, and the log. 09:44 09:52 10:00

In this context, the system “learning” means updating its stored sources, wiki interpretations, and instructions. The transcript describes no retraining of the underlying model. The distinction makes the architecture easier to reproduce: the changing state lives in inspectable files.

A reproduction gap: the video demonstrates karpathy-ingest, and an earlier autocomplete description says it updates source, principle, method, index, hot, and log pages and can run a lint pass. However, the extracted setup prompts do not include a readable prompt creating that skill. Prompt 04 explicitly creates karpathy-teach. A reproduction would need an additional ingestion-skill implementation; its missing creation prompt has not been invented here.

THE TAKEAWAY10:09 10:25

Understanding remains the learner's task

The video compresses its argument into four broad moves: capture public expert work, compile it into a wiki, codify recurring rules with source support, and run the method on real tasks. The six-prompt build is the practical packaging of those moves; review and ingestion extend the demonstration.

The strongest transferable idea is that an expert-informed assistant needs both a knowledge structure and a procedure. Source pages help establish what a recommendation rests on. Explicit rules shape how the agent approaches a problem. Execution records reveal what the implementation did. Keeping those parts connected lets a learner inspect the reasoning rather than rely on the confidence of the final answer.

The closing sentiment, attributed to Karpathy by the narrator, is that outsourcing thinking cannot outsource understanding. In the demonstrated workflow, that understanding is pursued by predicting a result, observing a run, recognizing a failure, and explaining a repair.

ANALYST'S SUGGESTION

For a solo AI project, test this pattern on one narrow topic before collecting an enormous corpus. Use a small set of well-chosen sources and one task with inspectable results. After the agent teaches it, change the input and ask yourself to predict the new result before running anything. Your ability to explain that variation is a useful additional test of understanding; the agent's own seven-rule score alone cannot establish it.
